# v0.1 plan

Status: M0 is done (see [03-m0-results.md](03-m0-results.md)). M1 is next. Read
[00-lessons-from-old-attempt.md](00-lessons-from-old-attempt.md) for why, and
[01-engine-architecture.md](01-engine-architecture.md) for the design.

## Goal of v0.1

A command-line engine that takes a prompt in a git repository, runs it through a
preset team of subscription models (orchestrator, worker, tester), and ends with
a checked diff the user can apply. It must be reliable on a small task suite and
come with measured numbers against a single-model baseline.

Not in v0.1: the TUI, local models, the "council of orchestrators", worker
swarms, and the advanced static-analysis ideas. See "After v0.1" below.

## Working rules

1. Every milestone ends with a command that works on real subscriptions. No
   milestone is "done" on fake backends alone.
2. Measure before building the next layer. The baseline numbers exist before any
   orchestration code does.
3. Engine failures and task failures are counted separately. A model writing
   wrong code is a task failure. A crash, a hang, a lost run or a leftover
   process is an engine failure, and those must reach zero.
4. Nothing is added to the engine unless it moves a number on the task suite.
5. Notes and logs stay short. No hashes, no evidence vaults.
6. Gemini first. Development runs, workers and testers use the Google
   subscription. Claude is used for the expert role and for the `solo`
   baseline, which is run once and kept. GPT is used only by the `trio` preset.

## Milestones

Each one builds on the one before. Sizes are rough working sessions, not dates.

### M0. Repo and backend conformance (done 2026-11-11)

Build: project skeleton, the backend interface, the fake backend, and adapters
for Claude Code, Codex, Gemini CLI and Antigravity. A `neuromesh doctor` command
that runs a probe set against every backend and model in a scratch git repo:

1. Returns an answer that matches a JSON schema.
2. Creates and edits a file with write access.
3. Runs a shell command and sees its output.
4. Stays inside its working directory; read-only mode really cannot write.
5. Reports usage numbers (and how many tokens an empty session costs).
6. Can resume a session.
7. Cancel kills every child process.
8. Quota, login and permission errors are recognised as such.

Done when: `neuromesh doctor` prints a capability table, at least one model per
role passes every probe, at least two different backends pass, and every failure
is written down with its exact message. A backend that fails is left out of the
presets. This is the gate that the old attempt never had: Antigravity's refusal
to write files would have been found here on day one.

### M1. Walking skeleton with one agent (2 sessions)

Build: `neuromesh run "<prompt>" --preset solo`. Run folder and event log, one
worktree, one agent, engine checks, diff shown, `neuromesh apply`,
`neuromesh resume`, cancel, quota pause.

Done when: five hand-picked small tasks run from prompt to applied diff with no
engine failure, and a run that is killed halfway resumes correctly.

### M2. Task suite and baselines (2 to 3 sessions)

Build: the task format, 15 to 20 tasks, and `neuromesh eval`.

Each task is a folder: a small seed repository, a prompt, hidden tests that are
copied in only after the run, and a short config. Planned mix:

| Kind | Count | Why |
| --- | --- | --- |
| Bug fix with a failing behaviour | 5 | The everyday case |
| Add a feature to an existing module | 5 | Needs reading the code first |
| Multi-file feature that splits into 2 or 3 tasks | 4 | Where a team should help |
| Refactor that must keep behaviour | 2 | Tests discipline |
| Small new command-line tool from scratch | 2 | Greenfield |
| Trivial request | 2 | Should *not* trigger a team; tests intake |

Languages: TypeScript and Python, with one or two in Rust.

Recorded per task and preset: pass or fail on hidden tests, wall time, tokens
per role and model, API-equivalent cost, repair rounds, escalations, and how it
ended. The runner goes task by task, can resume, and records a task as skipped
when quota runs out rather than failed.

Done when: `solo` and `solo-cheap` have each run the whole suite and there is a
results table. If `solo-cheap` passes nearly everything, the tasks are too easy
and get replaced before moving on.

### M3. Orchestrator and workers, in sequence (3 sessions)

Build: the plan schema, read-only planning, one worker per task in its own
worktree, engine checks after each, merge into the run branch, the `duo` preset,
and a final summary.

Done when: `duo` runs the whole suite with zero engine failures, and its results
sit in the table next to the baselines.

### M4. Tester, repair loop, escalation (3 sessions)

Build: the tester role and verdict schema, findings fed back to the worker
session, the stagnation breaker and the autopsy bundle (both ported from the
Rust research with the same rules and test cases), and the `factory`,
`google-only` and `trio` presets.

Done when: the v0.1 exit criteria below have been measured for `factory`.

### M5. Intake and parallel work (2 sessions)

Build: repo profile and size rules, preset suggestion, the small-request
shortcut (worker plus engine checks only), and parallel execution of tasks with
non-overlapping owned paths, two or three at a time.

Done when: both trivial tasks are routed to a single worker, the multi-file
tasks run their independent parts in parallel and merge cleanly, and wall time
on those tasks is lower than in M4.

### M6. Hardening and release (2 sessions)

Build: fix whatever the suite keeps hitting, a README with the measured table,
install instructions, and a tag.

Done when: the exit criteria hold.

## v0.1 exit criteria

| | Criterion | Target |
| --- | --- | --- |
| E1 | Reliability | Three full suite runs of `factory` in a row with zero engine failures |
| E2 | Quality | `factory` passes at least as many tasks as `solo`, minus one at most |
| E3 | Efficiency | Expert share (tokens on the heaviest model) is at most half of `solo`'s, and API-equivalent cost is reported next to it |
| E4 | Recovery | A run stopped by quota or by a kill resumes and finishes |
| E5 | Restraint | Trivial requests never start an orchestrator |

E2 and E3 are first targets. They are set before any measurement exists, and the
honest outcome may be that the team ties or loses on small tasks. Anthropic's
own write-up says most coding work has fewer parallel parts than research and
that multi-agent setups burn many more tokens. If the numbers come out that way,
the suite will show exactly where, and that is what the next version works on.
The long-term target from the landscape document (same pass rate at 15 to 30
percent of the cost) stays the direction, not a v0.1 promise.

## Risks

| Risk | What we do about it |
| --- | --- |
| Subscription quota is the real limit. A full suite across several presets may not fit in one quota window. | Small tasks, resumable eval runs, pause on quota, baselines run once and kept, `--tasks` to run a subset. |
| A CLI refuses writes or commands in headless mode, as Antigravity did. | Solved in M0 for all three backends. `doctor` is rerun after any CLI update. |
| Antigravity is the only route to Gemini, and Gemini is meant to do most of the work. | If it breaks, workers fall back to the cheap tiers of Claude or Codex by changing the preset. |
| Workers on Antigravity and Claude Code are not confined to their folder. | Work happens in a disposable worktree, the diff scope is checked, and the user reviews the diff before applying. Stronger confinement is an open item. |
| Fixed overhead per agent session makes small delegations more expensive than doing the work directly. | Coarse tasks, the small-request shortcut, and overhead measured per backend in M0. |
| CLI updates change flags or output. | Adapters are small, the tested versions are recorded, and `doctor` reruns after any update. |
| Scripted use of a subscription may be limited by a provider's terms. | Only documented headless modes are used. The owner should confirm each plan's terms before heavy eval runs. |
| The team does not beat the single model. | We find out at M4 for the price of a few suite runs, with data on where it loses. |
| Scope creep back into TUI work. | The TUI does not start until E1 to E5 hold. |

## After v0.1

**v0.2, product:** the TUI as a reader of the event stream, using the Signal
Studio pack as a visual reference rather than a spec; local models through
OpenCode or Ollama; a direct API backend.

**Research track** (kept in `research/`, promoted into the engine only when it
improves suite numbers). The first research job, right after M4, is to wrap the
existing Rust kernel as an analyzer plugin and measure it on the suite's Rust
tasks; see "Reusing the Rust research" in the architecture document. The six
unsolved items from the landscape document map like this:

| Landscape item | In v0.1 | Research |
| --- | --- | --- |
| 3.1 Complexity routing | Size rules plus the orchestrator marking hard tasks | Code-graph complexity estimator |
| 3.2 Contract-first parallel work | Parallel only on non-overlapping paths | Frozen interface stubs, public-surface lock, bisection of failing patch sets |
| 3.3 Stagnation breaker | Failure signatures and pass-count progress, any language | AST-normalised state hashing |
| 3.4 Failure autopsy | Yes | Measuring how much it saves against a cold start |
| 3.5 Zero-token fault localisation | No | Repo map for briefs, coverage-based localisation |
| 3.6 Architecture and performance gates | The project's own lint, types and tests | Import-boundary and complexity gates |

Also research: the council of orchestrators and the worker swarm from the
"future version" sketch.
