EdgeMed only runs on macOS today: the vault is an encrypted disk image mounted with `hdiutil`, secrets live in the macOS keychain, the Qdrant server binary is the macOS ARM64 one, and the asset provisioning script refuses any other platform. Add verified 64-bit Unix targets: macOS ARM64 and x86-64, and Linux ARM64 and x86-64, failing closed everywhere else.

What to build:

- A new module `edgemed/platforms.py` with `target(system=None, machine=None)`. Defaults come from `platform.system()` and `platform.machine()`. The machine is lower-cased: `arm64` or `aarch64` means `arm64`, `x86_64` or `amd64` means `x86_64`, anything else raises `RuntimeError("Unsupported native architecture: <machine>; 64-bit ARM or x86-64 is required")`. The system `Darwin` gives `macos-<arch>`, `Linux` gives `linux-<arch>`, anything else raises `RuntimeError("Unsupported native operating system: <system>")`. So `target("Darwin", "x86_64") == "macos-x86_64"` and `target("Linux", "aarch64") == "linux-arm64"`, while `target("Linux", "i686")` and `target("Linux", "armv7l")` raise an error that mentions 64-bit.
- `assets-manifest.json` gains a `qdrant_binaries` object keyed by target (`macos-arm64`, `macos-x86_64`, `linux-x86_64`, `linux-arm64`), each entry holding `archive` (release file name), `archive_sha256` and `binary_sha256`. Use the values that are already pinned for macOS ARM64 (archive `qdrant-aarch64-apple-darwin.tar.gz`, binary hash from the current `.tools/qdrant` entry, which moves out of `files`) and, for the others, the Qdrant v1.19.1 release archives `qdrant-x86_64-apple-darwin.tar.gz`, `qdrant-x86_64-unknown-linux-gnu.tar.gz` and `qdrant-aarch64-unknown-linux-musl.tar.gz` (take their hashes from the release page; they are not needed by the grading tests, which use synthetic manifests).
- `scripts/provision_assets.py`: use `target()` instead of the macOS ARM64-only check (import it from `edgemed.platforms`, adding the repository root to `sys.path`). `--model-only` stays as it is. Without it, look up `manifest["qdrant_binaries"].get(target())`; if there is none, raise `RuntimeError("No verified Qdrant binary for this platform; use --model-only")`. Otherwise, after the model files, make sure `.tools/qdrant` exists with the pinned `binary_sha256`: if it does not, download the pinned archive `https://github.com/qdrant/qdrant/releases/download/v<qdrant_server>/<archive>` (through the module's `download`, which checks `archive_sha256`) into a temporary directory inside `.tools`, extract the single regular member named `qdrant` (refuse an archive with zero or several such members, or one over 256 MiB, as "Unexpected release archive"), check its sha256 against `binary_sha256` ("Qdrant binary checksum mismatch"), write it with mode 0o755 and move it into place atomically. A second run with the right binary in place must make no request. Print "Pinned model and Qdrant assets verified; no runtime records or keys were changed."
- `edgemed/operations.py`, `preflight(project)`: besides the file checks it already does, require `.tools/qdrant` to exist and match `manifest["qdrant_binaries"][target()]["binary_sha256"]`, otherwise raise `RuntimeError("Pinned Qdrant binary missing or checksum mismatch for this platform")`. The returned summary reports `"platform": target()` and counts the binary in `asset_hashes` (one more than the number of manifest `files`). `cold_backup` stays macOS only and raises `RuntimeError` with a message saying a Linux backup needs an offline LUKS volume snapshot.
- `edgemed/linux_vault.py` (new): `verify_luks_mount(vault: Path)` fails closed on Linux. The mapper name comes from the environment variable `EDGEMED_LUKS_MAPPER` (default `edgemed-vault`) and must match `[A-Za-z0-9_.-]{1,64}` ("Invalid EDGEMED_LUKS_MAPPER"). The vault must be a mount point and not a symlink ("Linux vault is not an independently mounted LUKS volume"). Its mount source (module-level helper `_mount_source(vault)`, which runs `findmnt -n -o SOURCE --mountpoint <vault>`) must start with `/dev/` and resolve to `/dev/mapper/<mapper>` ("Vault mount is not backed by the configured LUKS mapper"). The mapper's device-mapper UUID (module-level helper `_mapper_uuid(device)`, read from `/sys/dev/block/<major>:<minor>/dm/uuid`, empty string if missing) must start with `CRYPT-LUKS2-` ("Vault device is not a verifiable LUKS2 mapper"). Finally the directory must be owned by the current user and not accessible by group or others ("Vault mount must be owned by this user and accessible only to this user"). Return `True` when everything holds. The helpers must be looked up as module attributes at call time, because tests replace them.
- `edgemed/cli.py`: `verify_vault()` calls `target()` first, then on Linux calls `verify_luks_mount(VAULT)`, on macOS keeps the `hdiutil` check, and on any other platform raises `RuntimeError("Only macOS and Linux 64-bit launchers are supported")`. `mount_vault()` calls `target()` and, on Linux, only verifies (the operator mounts the LUKS volume themselves). The default runtime directory is `~/Library/Application Support/EdgeMed Local` on macOS and `$XDG_DATA_HOME/edgemed` (default `~/.local/share/edgemed`) elsewhere, still overridable with `EDGEMED_RUNTIME`. The `lock` and `backup` commands stay macOS only: on Linux they exit through `parser.error` with a message about stopping EdgeMed and unmounting the LUKS vault with system tooling, and about needing an offline LUKS volume snapshot.
- `edgemed/security.py`: add `protected_keyring()`, which imports `keyring` and, on Linux, accepts only a backend whose class module is `keyring.backends.SecretService` or `keyring.backends.kwallet`; any other backend (for example a plaintext file fallback) raises `RuntimeError("Linux requires an unlocked Secret Service or KWallet keyring; plaintext fallback is disabled")`. It checks `sys.platform` at call time. `load_secret` and `save_secret` obtain `keyring` through it.
- `pyproject.toml`: pin `onnxruntime==1.23.2` for `sys_platform == 'darwin' and platform_machine == 'x86_64'` and `onnxruntime==1.30.0` for every other platform (environment markers).

Graded by two test files, `tests/test_provision_assets.py` (rewritten for the new behaviour) and `tests/test_unix_platform.py` (not in your copy of the repository). They cover: the `target()` table above; a model-only provisioning run and a full Linux provisioning run against a synthetic manifest and synthetic archive (the full run with `target` patched on the script module to return `linux-x86_64`, and the archive fetched from the exact release URL, once only); a checksum failure that keeps the old file; `verify_luks_mount` on an unmounted directory, on a patched mount with a wrong mapper UUID prefix and a wrong mount source, and on a correct one; `protected_keyring` with a backend class that is not a system keyring; and `preflight` with the native binary checksum wrong ("Qdrant binary missing or checksum mismatch" is a prefix of the message they match).
