EdgeMed's local retrieval (`edgemed/retrieval.py`) is slow and memory hungry once a clinic holds around ten thousand records. Every search that misses its cache rebuilds a tuple of per-document token counters, and the hybrid lexical score (BM25) is computed by looping over every document for every query term. The in-memory cache also refuses to hold a corpus above a conservative 32 MiB estimate, so large corpora are rebuilt on every query. Make it scale without changing any search result.

Behaviour that must stay exactly the same: the lexical score of a revision for a query is the same BM25 formula as today (term set of the query, `idf = log(1 + (N - df + 0.5) / (df + 0.5))`, term frequency saturation with k1 = 1.5, b = 0.75 and the 2.5 numerator factor, average document length floored at 1), the dense search, the fusion and the payload of results. Existing callers and tests must keep working.

What to build:

- A `LexicalCorpus` class in `edgemed/retrieval.py`, constructed as `LexicalCorpus(records, revisions)` where `records` is what `store.current_records(owner, subject)` returns and `revisions` maps a revision id to `(memory_id, revision_dict)`. It precomputes an inverted index and exposes, as plain attributes: `records`, `revisions`, `num_docs` (the number of revisions), `postings` (token to a dict of revision id to term frequency), `lengths` (revision id to token count), `total_tokens`, `avg_len` (`total_tokens / max(1, num_docs)`) and `eligible` (the Qdrant `Filter(must=[HasIdCondition(set(revisions))])` built once for the corpus, or `None` when there are no revisions or the filter cannot be built). It has `estimate_bytes()`, a conservative size estimate derived from the postings, lengths, revisions and record contents. `tokens(text)` keeps its behaviour (lowercase runs of `[a-z0-9]`) but should use a pre-compiled regular expression.
- Backward compatibility: iterating a `LexicalCorpus` must still unpack as the old 6-tuple `(records, revisions, docs, lengths, df, avg)`, where `docs` is a dict of revision id to `Counter` of tokens and `df` a `Counter` of the number of revisions containing each token. `Retrieval._corpus` stays available as a property that returns `(key, corpus)` for the cached corpus (or `None`), where the key is `(owner, subject, store.generation)`; assigning to it replaces the cache (`None` clears it). `clear_cache()` empties the cache.
- `Retrieval._load_corpus(owner, subject)` returns a `LexicalCorpus` and caches it per `(owner, subject, store.generation)`, so several owners and subjects can be cached at the same time (keep a small bound, for example 8 entries) and loading one subject must not evict the general corpus of the owner. A repeated load for the same key and generation returns the very same object without touching the database. Every canonical write advances `store.generation`, and corpora of older generations must be dropped so a load after a mutation reflects it. The cache limit becomes 256 MiB, overridable with the environment variable `EDGEMED_MAX_LEXICAL_CACHE_MB`; an oversized corpus is still returned but not cached.
- Persistent cold-start cache: for the general corpus of an owner (`subject is None`), write the postings, lengths, token total, records and revisions, tagged with the owner and the store generation, to `<store.root>/lexical_<owner>.cache` (use `pickle`); on a fresh `Retrieval` over the same store, if that file exists and matches the current generation and owner, rebuild the `LexicalCorpus` from it instead of recomputing, and fall back to a normal rebuild if the file is unreadable or stale.
- `search` should use `corpus.postings` and `corpus.eligible` for the lexical half and the dense filter. It should stop collecting fused results as soon as `limit` distinct memories were chosen. `drain` should take an optional `batch_size` (default 32, it used to process 4 jobs per call).

Graded by a new test file, `tests/test_retrieval_performance.py` (not in your copy of the repository). It builds `Retrieval` with a fake embedder (so no model is needed) and checks: the inverted-index scores equal the baseline formula to 1e-9; a 10,000-record store is cached (`estimate_bytes()` under 100 MiB, the second `_load_corpus` returns the same object, `eligible` is set); cache invalidation after `store.revise`; cache isolation between the general corpus and two subjects; the on-disk cache is created and a second `Retrieval` recovers an equal corpus (same `num_docs`, `total_tokens`, `postings` keys and `lengths`); and the tuple unpacking, `_corpus` property and setter, and `clear_cache()`.
