After a built program is reviewed, the reviewer's findings go to the last task's worker, usually the cheapest model, whatever file the findings name. In the first three-tier run, a flaw in the senior tier's number formatting went to Haiku, which documented it as a known difference instead of fixing it and then spent 19 minutes on it. Send a finding to the rung that built the file it names.

- In `src/engine/run.ts`, add `strongerOwner(state, task, findings)`. For findings that name a file (`finding.file`, compared after trimming whitespace and a leading `./`) that another task of the run owns (`owned`), it returns the highest worker-ladder rung (`state.workerLadder`) among those other tasks that is above this task's own rung, together with the file; a task that is the expert's or was escalated counts as the top rung of the ladder. It returns nothing when this task is itself the expert's, was escalated or advised, there is no ladder, or this task's rung is already enough.
- Move the climb out of `onStuck` into a function `climbTo(run, task, rung, reason, feature?)`, which a stuck worker's climb to the next rung uses too: the task moves to that rung with round 0, fresh progress, `next` set to "climb", no session, step "agent", and a `task.climbed` event with the `from` and `to` models and the reason (and `feature` when given).
- When a review of a task fails and `strongerOwner` finds a rung, climb there with a `task.climbed` event tagged `feature: "F79"` and the reason "the reviewer's findings are in <file>, which a stronger developer built", instead of repairing on the current rung; the fresh session is told the findings.
