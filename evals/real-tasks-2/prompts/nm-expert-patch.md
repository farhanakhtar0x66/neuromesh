When a worker's checks pass but the reviewer's findings are still open after the repair rounds, the expert takes the task over and rebuilds it from the start, which is what made every expensive build expensive. Let it fix the findings in the worker's code instead.

- In `src/engine/prompts.ts` add `patchPrompt(state, task)`: "You are the lead engineer. A worker built the task below and the project's checks pass, but a reviewer found problems the worker could not fix. The current directory holds the worker's code.", then the request (or the overall request, the task's title and brief when the task is a part of a larger build), "The reviewer's latest findings:" with the latest findings as text, the earlier findings that are not minor "for context (some may be fixed already)" when there are more of them (the last 6), the working context and the tools note, then the instruction "Fix these problems with the smallest changes that do it. Keep the worker's structure and everything that already works; do not rewrite or restyle working code. If a finding is wrong, leave the code as it is and say why in your notes.", then the checks and the worker rules.
- In the engine (`src/engine/run.ts`, the `escalate` step; `TaskState` in `src/engine/types.ts` gets `patch?: boolean`): when the project's checks pass and the last review left findings, set `task.patch` and do not reset the worktree to the task's base; the escalated expert's prompt is then `patchPrompt` instead of the escalation prompt. The `task.escalated` event carries `patch`, and `feature: "F14"` when it is a patch.
